## Задание 3. Объяснение через GIL

**GIL** (Global Interpreter Lock) — блокировка в CPython: в каждый момент байт-код Python выполняет **только один поток** процесса.

- **Почему потоки не ускоряют счёт.** Разбор чисел и сложение — работа процессора на Python. Четыре потока по очереди захватывают GIL и работают не одновременно, а поочерёдно, плюс тратят время на переключения. Поэтому 4 потока даже немного медленнее одного (0.72 против 0.68 с).
- **Почему потоки ускоряют ввод-вывод.** Пока поток ждёт ответа от сети (системный вызов, ожидание в ядре), он **отпускает GIL**, и работают другие потоки. Четыре запроса ждут одновременно: 20 URL / 4 × 0.5 с ≈ 2.5 с вместо 10 с.
- **Почему процессы ускоряют счёт.** У каждого процесса свой интерпретатор и **свой GIL**, поэтому они действительно работают параллельно на разных ядрах. На 2 ядрах теоретический максимум — 2×; получили 1.39×.
- **Почему процессы дороже.** Нужно создать процессы и запустить в каждом интерпретатор Python, передать аргументы и результаты между процессами (сериализация pickle), каждый процесс занимает свою память. Поэтому в сетевой задаче процессы чуть медленнее потоков (2.57 против 2.53 с), а в счёте ускорение меньше 2×. Ядер всего 2, поэтому 4 процесса не могут работать одновременно — лишние ждут очереди.

## Задание 4. Потоки разделяют память, процессы — нет

```
Способ запуска процессов: forkserver
Родитель до:             data = []
  внутри (поток): data = ['поток']
Родитель после потока:   data = ['поток']
  внутри (процесс): data = ['процесс']
Родитель после процесса: data = ['поток']
```

- Поток работает в **том же адресном пространстве**, поэтому его изменение списка `data` сразу видно родителю.
- Процесс имеет **своё адресное пространство**. В Python 3.14 процессы по умолчанию создаются через `forkserver`: дочерний процесс заново загружает модуль, и у него свой пустой список — поэтому внутри видно только `['процесс']`. Изменение не возвращается в родителя: после процесса у родителя всё ещё `['поток']`. Для обмена данными процессам нужны специальные средства (очереди, pipe, общая память).

## Выводы: когда использовать потоки, когда процессы

| Ситуация | Что использовать | Почему |
|---|---|---|
| Ожидание ввода-вывода: сеть, диск, базы данных | **Потоки** | во время ожидания GIL отпускается; потоки дешёвые и разделяют данные |
| Вычисления на Python (CPU-задачи) | **Процессы** (не больше числа ядер) | каждый процесс со своим GIL работает на своём ядре |
| Нужна изоляция: сбой одной части не должен уронить остальные | **Процессы** | отдельная память |
| Много мелких задач с общими данными | **Потоки** | не нужно копировать данные между процессами |

## Контрольные вопросы

**1. Что общего у потоков одного процесса и что у каждого своё?**
Общее: адресное пространство (код, глобальные переменные, куча), открытые файлы и сокеты, текущий каталог, обработчики сигналов, PID процесса и права пользователя.
Своё у каждого потока: стек, регистры процессора (включая счётчик команд), идентификатор потока (TID), маска сигналов, локальные данные потока (thread-local) и состояние для планировщика.

**2. Почему в CPython 4 потока не ускорили счёт, а 4 процесса ускорили?**
Из-за GIL: в процессе байт-код Python в каждый момент выполняет только один поток, поэтому четыре вычисляющих потока работают по очереди. У каждого процесса свой интерпретатор и свой GIL, поэтому процессы считают действительно параллельно на разных ядрах (здесь их 2).
